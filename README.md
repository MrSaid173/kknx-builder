# KKNX builder (mi439: Redmi 8 / 8A, olive / pine)

Собирает то же ядро, что ваш `KKNX-800Mhz_v2`, но с настраиваемыми параметрами: частоты GPU,
ReSukiSU + SUSFS + NoMount (любая версия), порт LOLZ (lite / full), панели, Dummy LiveDisplay и FixLabels.
CPU-частоты **не меняются**: скрипт сверяет контрольную сумму всех CPU-таблиц до и после и прерывает сборку при расхождении.

Исходники берутся при сборке: `danya2271/kernel_xiaomi_sdm439` на коммите `124dcdc99803`.
Это тот самый коммит, что зашит в версию вашего бинарника.

## Запуск

1. Создайте репозиторий на GitHub, залейте туда содержимое этого архива.
2. **Actions → Build KKNX kernel (mi439) → Run workflow**, заполните поля (15 полей; GitHub разрешает до 25 с декабря 2025).
3. Готовый `KKNX-gpu…zip` лежит в Artifacts. Прошивается через recovery, как обычный AnyKernel3.
   Рядом лежит `build-info.txt`: в нём точные SHA ReSukiSU, SUSFS и NoMount, которые вошли в сборку.

## Поля запуска

| Поле | По умолчанию | Смысл |
|---|---|---|
| `gpu_freqs` | `904,560,510,400,320` | 5 уровней GPU в МГц, сверху вниз. 904 это максимум и ровно то, что реально выдают KKNX и Kuroneko |
| `gpu_pll_mhz` | пусто | только для контрольной сборки: PLL верхнего уровня GPU. `1808` вместе с `gpu_freqs=800,…` даёт GPU-часть KKNX-800Mhz_v2 |
| `toolchain` | `ubuntu_cruel` | clang Ubuntu + binutils/gcc автора (`aarch64-cruel-elf`); `ubuntu_clang16` = всё из Ubuntu; `neutron` = как у автора, не проверен |
| `root` | `resukisu_susfs` | `resukisu_susfs` = ReSukiSU + SUSFS; `none` = без root. Оригинального KernelSU больше нет |
| `resukisu_ref` | пусто | версия ReSukiSU: тег (`v4.1.0`), ветка или полный SHA. **Пусто = последний коммит основной ветки** |
| `susfs_ref` | пусто | версия SUSFS (`wxx9248/susfs4ksu`): тег, ветка или SHA. **Пусто = последний коммит ветки `kernel-4.9-v2`** (порт под 4.9; она же ветка по умолчанию репозитория) |
| `nomount` | да | встроить NoMount (только при `resukisu_susfs`) |
| `nomount_ref` | пусто | версия NoMount (`maxsteeel/nomount`): тег, ветка или SHA. **Пусто = последний коммит основной ветки** |
| `lolz_port` | `lite` | `off` / `lite` / `full`, см. раздел «Порт LOLZ» |
| `lolz_panel` | да | панели экрана как у LOLZ (60 Гц). Работает при `lolz_port` = lite/full |
| `livedisplay` | да | прошить Dummy LiveDisplay sysfs HAL (как отдельный zip, после ядра) |
| `fixlabels` | да | выполнить fixlabels последним шагом установки |
| `localversion` | `-KKNX-V3.x.x` | суффикс `uname -r` |
| `kernel_ref` | `124dcdc…` | коммит ядра danya2271 |
| `defconfig` | `kuro439_defconfig` | конфиг KKNX (DT overlay, wireguard). **Не меняйте на olive-stock**, см. ниже |

Версии берутся скриптом `scripts/resolve_ref.sh`: он превращает тег/ветку/пусто в полный SHA, и дальше везде используется SHA.
Если «последняя» версия когда-нибудь сломает сборку, возьмите SHA из `build-info.txt` прошлой удачной сборки и вставьте в поле.

## Порт LOLZ

Сравнение шло по вашим бинарникам LOLZ-V24 и KKNX-800Mhz_v2, затем по DTB и dtbo, собранным из исходников.
Исходники на коммите `124dcdc` соответствуют вашему бинарнику KKNX (в DT: ADSP 4 МБ, `mem_dump`, без `linux,cma`, экран с dynamic fps),
поэтому патчи нужны все. Скрипты идемпотентные и строгие: что уже сделано, пропускают, а если файл не такой, как ожидалось, падают.

| Что | off | lite | full |
|---|---|---|---|
| DT: CMA 64 МБ (`linux,cma-default`), ADSP 16 МБ, без `mem_dump` | | да | да |
| bootargs: `quiet kpti=0 rcu_nocbs=0-7 noirqdebug` как у LOLZ. Строка KKNX заменяется **целиком**: пропадают `sched_enable_hmp=1`, `nosoftlockup`, `mce=ignore_ce`, `nodebugmon` | | да | да |
| `init.lolz.rc` в `/vendor/etc/init` (дисплей `msm_fb_dispparam 0010`) | | да | да |
| HZ 180 → 300 | | | да |
| `MODULES=y` + `BPF_JIT=y` (BPF_JIT в этом дереве зависит от MODULES) | | | да |
| `CRYPTO_ZSTD=y` и zram по умолчанию на zstd (если zstd включён) | | | да |

Не меняется ничего, что относится к разгону: частоты CPU и GPU, напряжения CPR, `busy-cost-data`, таблицы шины.

**Панели (`lolz_panel`, отдельное поле).** В исходниках KKNX у двух панелей «c3i» повышена частота кадров. LOLZ держит их на штатных 60 Гц.
Какая панель стоит в вашем телефоне, я не знаю: если другая (например hx8399c, у неё в KKNX и LOLZ одинаковые настройки), поле ничего не изменит.
- ili9881h: частота кадров 76 → 60;
- nvt36525b: 65 → 60, убран dynamic fps (30..65), `h-sync-pulse` 0 → 1, включён ESD-контроль;
- DSI PLL `ssc-frequency-hz` 35500 → 31500.

Правится исходник панели, поэтому базовые DTB и dtbo получаются согласованными (dtbo собирается из исходников, `make dtbo.img`).
Выключите поле, если хотите оставить разгон экрана как в KKNX.

**Уже есть в KKNX и не трогается:** OVERLAY_FS (по вашему запросу остаётся как есть), MEMBARRIER, UTS_NS, BLK_CGROUP, CFS_BANDWIDTH.
Я ошибался в прошлых ответах, когда говорил, что этих опций нет: смотрел конфиг, вшитый в старый бинарник, а он устаревший.

**Сознательно не портировано** (решение за вами, если нужно): SCHED_WALT (другой планировщик, чем в KKNX), `cfq` вместо `noop`,
SECCOMP и прочие опции безопасности LOLZ, отладочные опции (KPROBES, ftrace), jtag-узлы DT. `clock-frequency` в узлах CPU у LOLZ равен их штатным
максимумам (1459 / 2016 МГц), то есть это часть настроек частот, которые вы просили не трогать. `deep-nap-timeout` GPU в разговоре не обсуждался.
Часть из этого может быть полезной, но на железе я ничего из этого не проверял.

## Установщик (AnyKernel3)

Порядок такой, как если бы вы прошивали отдельные zip по очереди:

1. ядро: определение разделов, правка cmdline, `init.lolz.rc` (если порт LOLZ включён), чистка `*.ko`, `flash_boot`, `flash_dtbo`;
2. `sync`;
3. Dummy LiveDisplay: только после чистки `*.ko`, иначе `rdbg.ko` и `efivarfs.ko` были бы удалены. Если sysfs HAL в `/vendor` нет, шаг пропускается (оригинальный zip в этом случае прерывался, здесь ядро к этому моменту уже прошито);
4. `sync`;
5. FixLabels **последним**: `chcon` для `/data/data` и `/data/user_de/0` (`system_data_file`) и `/data/misc/profiles/cur/0` (`user_profile_root_file`), только эти три каталога, не рекурсивно. До 5 секунд ожидает появления каталогов. Если `/data` не смонтирован или не расшифрован, шаг пропускается;
6. `sync`.

В recovery должен быть `chcon` (в busybox из AnyKernel3 его нет, берётся `toybox`/системный). Если метку поставить не удалось, установщик пишет об этом и продолжает.

## GPU: что на самом деле происходит с частотой

Метка частоты (в DTS и в таблице `clock-gcc-8952.c`) и реальная частота это разные вещи. Реальную задаёт PLL gpll3
с делителем /2, то есть **реальная частота = PLL / 2**. Сверка по таблицам обоих ядер:

| ядро | метка | PLL | реально |
|---|---|---|---|
| Kuroneko v3.0.2 | 870 МГц | 1808 МГц | 904 МГц |
| KKNX-800Mhz_v2 | 800 МГц | 1808 МГц | 904 МГц |
| стоковые уровни (560, 510…) | 560 | 1120 | 560 (метка честная) |

То есть оба ядра **физически работают на 904 МГц**, а 870 и 800 это просто разные подписи. PLL 1808 МГц выбран не случайно:
это максимум, который разрешает fmax самого PLL. Сборщик по умолчанию ставит метку 904 и PLL 1808: железо настроено ровно как у KKNX и Kuroneko,
а метка теперь честная.

- Правило сборщика: PLL = 2 × метка. Допустимо 350–904 МГц (потолок 904 задаёт fmax gpll3). Значения вне диапазона отклоняются.
- Значения ниже 904 (например 850) дают другую настройку PLL, чем у KKNX, это отдельный, непроверенный на железе режим.
- Меняется только узел `speed-bin 0`. Остальные узлы GPU не трогаются.
- `gpuclk` в sysfs показывает значение из DTS, а не измеренное. Измерять: `cat /sys/kernel/debug/clk/gcc_oxili_gfx3d_clk/measure` (нужен root).

## Напряжение CPU и GPU

Сравнение DTB ядер KKNX-800Mhz_v2 и Kuroneko v3.0.2 показало, что механизм одинаков: все поправки CPR (`quotient-adjustment`,
`virtual-corner-quotient-adjustment`, floor, карты corner'ов) совпадают до значения. Единственное отличие это потолок напряжения
верхних corner'ов: 960 мВ у Kuroneko и 950 мВ у KKNX (так же в исходниках ветки 1topaz, которую использует сборщик).
CPU-частоты (2616 / 2568 МГц) в обоих ядрах одинаковые.

Поэтому сборщик напряжение не меняет: получается ровно то, что у KKNX. Отдельные поля для андервольта убраны, чтобы
случайное значение не привело к зависанию. Код правки CPR остался в `scripts/apply_tuning.py` (переменные `CPU_UV_MV`, `CPU_CEIL_MV`,
`GPU_CORNER_FMAX`, по умолчанию не заданы). Если понадобится, их можно добавить в workflow; пределы безопасности в скрипте сохранены.

## Root-часть

- **resukisu_susfs**: ReSukiSU + SUSFS (порт `wxx9248/susfs4ksu`, ветка `kernel-4.9-v2`) + NoMount. Для `kuro439_defconfig`
  понадобились доработки, они применяются автоматически: старые ручные хуки удаляются (у SUSFS свои inline-хуки),
  в SELinux снимается `static` с нескольких символов (`export_selinux_symbols.py`, нужно при `KALLSYMS_ALL=n`),
  `disable_seccomp()` в ReSukiSU становится no-op при `CONFIG_SECCOMP=n` (`patch_resukisu_seccomp.py`).
  Версия ReSukiSU считается по числу коммитов, поэтому его история скачивается целиком (без файлов), а не `--depth 1`.
- **none**: заглушка вместо KernelSU и удаление старых хуков.
- NoMount встраивается built-in (`fs/nomount`, `CONFIG_NOMOUNT=y`), сам модуль ставится из менеджера как метамодуль.
- Оригинальный KernelSU (tiann) убран. Нужен менеджер ReSukiSU.

## Порядок проверки, если телефон не грузится

Каждый шаг меняет только одну вещь, так вы найдёте виновника. Перед прошивкой держите под рукой рабочий `KKNX-800Mhz_v2.zip`.

1. **Минимум:** `root=none`, `lolz_port=off`, `livedisplay=нет`, `fixlabels=нет`, `gpu_freqs=800,560,510,400,320`, `gpu_pll_mhz=1808`.
   Исходники, DTB и GPU-таблица те же, что у вашего рабочего ядра, но без root. Если не грузится, виноваты не частоты и не root, а компилятор или упаковка.
2. Не грузится на шаге 1: повторите с `toolchain=ubuntu_clang16`, затем с `toolchain=neutron`.
3. Грузится: `gpu_freqs=904,560,510,400,320` и пустой `gpu_pll_mhz`. Это честная метка при том же железе.
4. Дальше по одному: `root=resukisu_susfs`, затем `lolz_port=lite`, затем `lolz_panel`, затем `full`.
   Если после какого-то шага перестало грузиться или появились краши, виноват именно он. `livedisplay` и `fixlabels` работают в recovery и на загрузку ядра не влияют.

Важно: автор собирает с `CROSS_COMPILE=aarch64-cruel-elf-`, и ядро выводит из этого цель компиляции `--target=aarch64-cruel-elf`,
а обычная сборка даёт `aarch64-linux-gnu`. Режимы `ubuntu_cruel` (по умолчанию) и `neutron` повторяют подход автора.

## Какой defconfig нужен

Настоящий конфиг вашего ядра это `kuro439_defconfig` (`-KKNX-V3.x.x`, WireGuard, `CONFIG_BUILD_ARM64_DT_OVERLAY=y`).
Конфиг, встроенный в образ (IKCONFIG), устаревший: в нём заголовок 4.9.193 и `-perf`, а в самом образе есть WireGuard.
Поэтому ему верить нельзя.

Сборка с `olive-stock_defconfig` даёт 37 DTB с board-id вместо 15 базовых DTB в режиме overlay.
Загрузчик не находит подходящий DTB, и телефон уходит в fastboot. Шаг «Проверка результата»
(`verify_image.py`) теперь падает, если набор DTB не 15 штук или в них есть board-id.

## Фиксы дерева (scripts/fix_tree.sh)

В `mm/Makefile` ветки 1topaz стоит `obj-$(DEBUG_KERNEL) += debug.o` без префикса `CONFIG_`, то есть условие никогда не выполняется.
Заголовки (`mm/internal.h`, `include/linux/mmdebug.h`) при этом ждут `debug.o` только при `CONFIG_DEBUG_KERNEL=y`.
Скрипт заменяет строку на `obj-$(CONFIG_DEBUG_KERNEL) += debug.o`. С `kuro439_defconfig` (DEBUG_KERNEL выключен) файл не собирается,
как и раньше; с `olive-stock_defconfig` он нужен, иначе линковка падает на `pageflag_names`, `dump_page` и т. д.
Не заменяйте строку на `obj-y`: с `kuro439_defconfig` это ломает сборку.

## Что проверено, а что нет

Проверено в песочнице (одно ядро процессора, без полной сборки образа):
- на чистых исходниках `124dcdc` отработала вся цепочка патчей: фиксы дерева, root с последними версиями ReSukiSU / SUSFS v2.3.0 / NoMount, порт LOLZ (DT, панели, zram), тюнинг GPU;
- из пропатченного дерева собираются все 15 DTB и `dtbo.img` (20 записей); значения (bootargs, CMA, ADSP, отсутствие `mem_dump`, панели) совпадают с LOLZ, `verify_image.py` на них проходит и отклоняет «старый» dtbo;
- `.config` для режима full: все запрошенные опции (HZ_300, MODULES, BPF_JIT, CRYPTO_ZSTD) реально применяются; компилируются затронутые файлы (BPF JIT, `net/core/filter.c`, модульный загрузчик arm64, zstd, zram, SUSFS, NoMount, драйвер ReSukiSU и все файлы с хуками SUSFS);
- то же с тулчейном `ubuntu_cruel` (binutils/gcc автора) и clang 16.0.6 из Ubuntu;
- порядок шагов установщика, флаги «выкл», пропуски (нет HAL, нет каталогов `/data`) прогнаны в `busybox ash` с подставными `chcon`/`mountpoint`/`sync`.

**Не проверено:** полная сборка `Image.gz-dtb` с этими изменениями (в песочнице нет времени и ядер), загрузка на устройстве, работа `chcon` в вашем recovery,
режим `neutron` (из песочницы недоступен gitlab). Новое в `full` по сравнению с вашим KKNX (MODULES=y, HZ 300, zstd) на железе не пробовалось.
Расхождение компилятора с автором (у него Neutron clang 16.0.0) остаётся главным неисключённым отличием.
